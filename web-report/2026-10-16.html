The three questions for standup: (1) Who reviews 0902, and where do its open leaves go? The sprint has ended, 18 leaves are in review, and I309 and I311 have no sprint to move into. (2) Should main's mobile build be patched before BVA-I316 lands? Since #72, a call received with the app open shows a duplicate "Incoming call" banner that stays after the call ends (§3.1). (3) Who adds the call.ended handler on mobile? It is about ten lines, and without it the server's new teardown push does nothing.

The three things worth knowing:

1

0902 ran out without a close, and the queue grew after the end date. At 16:05 UTC on 15 Oct, about two hours after the sprint's last edition, board administration moved BVA-I307 (Deep Link Routing & Badge Count) and BVA-I313 (Notification Settings Screen) from In progress to REVIEW/QA, nine seconds apart and with no comment. I307's routing exists only on the unmerged BVA-I316 branch. On main, every push tap still opens Home. I313's screen has been on main since July; the open question last week was whether it matches the new design, and nothing on the board answers it. The sprint is not swept, and Zoho still lists no 0903. 18 of 21 leaves are now in review, and nothing has left review since 0902 opened. The bottleneck is the review step, not the developers.

2

beevia-api #72 fixes two real call faults on the server. First, the ring was gated on isUserOnline, which only asks whether a socket exists. A backgrounded app keeps its socket, so the push was dropped in exactly the case where the app could not show the call itself. Now call.incoming always goes out as a push as well as over the socket. Second, nothing told a backgrounded device that a call had ended. Now decline, end and the media server's room-closed event each send a silent call.ended (status: ended, declined or missed) to every member. That push ignores the call preference switches, which is the right call: there is no alert left to protect anyone from. The commit also repairs a test that had stubbed the ring out, and gives the two pushes separate dedupe keys so the teardown is not dropped as a duplicate of the ring. It shipped on push to production with no test gate, like every backend change since September, and no board item names it.

3

The client half is missing, and main is now slightly worse in one case. The server's own docs ask the client to "dedupe on callId". Mobile main does not. Its foreground handler shows a local banner for any push with a visible notification block (BVA-I312's work, in review). So a call received with the app open now shows the ringing screen and an "Incoming audio call" banner, which stays after the call ends. BVA-I316 already handles that case correctly. No branch handles call.ended. Both handlers ignore pushes that have no notification block, so a native ringing screen on Android is dismissed only by the socket or its own 30-second timeout. The VoIP token clash on BVA-I316 is unchanged (§3.2).

If you read nothing else: 0902 is over and unreviewed, with 18 of 21 leaves waiting and no sprint after it. The server now rings reliably and sends a teardown, but the mobile app on main shows a duplicate banner for calls taken in the foreground, and no build listens for the teardown yet.

The server is right; the client needs two small changes. On main, the foreground handler should skip call.incoming, as the branch does. On both, call.ended should call FlutterCallkitIncoming.endCall(callId); the branch already has CallKitManager.endNativeCall for this. Whether #72 is live cannot be seen here, but beevia-api deploys on every push to main.

One server detail to check. call.ended is the first push this API sends with no notification block. FcmPushAdapter sends silent pushes with contentAvailable but keeps apns-priority: 10. Apple's documentation asks for priority 5 on content-available-only pushes, so iOS may throttle or drop them. No iOS code consumes the push yet, so nothing breaks today. It cannot be tested from here.

Not changed by #72: call.incoming's data still has no caller name, so the native call screen would still say "Beevia" (last edition's recommendation 4). And the push still carries a visible notification block.
