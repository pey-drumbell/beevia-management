# Product

## Platform

web

## Stack

**Plain HTML and CSS. No JavaScript framework, no Babel, no build step, no backend, no dependencies.**

This is a page two people glance at. The user's standing instruction is whatever is easiest and fastest, and the simplest thing that fully satisfies the requirements is a static HTML file per date plus an index.

- **One self-contained `.html` file per report date**, in `web-report/`, alongside a single shared `styles.css`.
- **`index.html` lists the dated reports** as plain links. That is the entire archive — navigation only, per the confirmed scope.
- **The `beevia-refresh` skill writes the HTML directly**, in the same authored pass that already writes the Markdown report by judgement. No parser, no template engine, no transpiler, nothing to install or run.
- **JavaScript only where something genuinely needs it.** One classic script, `ui.js`, no dependencies: it measures which tables actually overflow so the "scrolls further" edge mark is never a guess. Everything else is static markup. Classic script, never `type="module"` — module scripts are blocked by CORS on `file://` and would break the double-click open.
- **No masthead graphic.** A canvas data-field was built here and removed at the user's request; the masthead is type and numeric rails. Nothing animates on entry.
- **Hand-written CSS** with custom properties for tokens. No framework, no PostCSS.

Consequences, all of them good here: the page opens by double-click from `file://` and works hosted anywhere static; there is no CORS problem because nothing is fetched; it loads instantly on a phone, which is what Product Principle 4 actually asks for; and any page stays hand-editable forever.

React with Babel Standalone was considered and dropped — roughly 2.7 MB of in-browser transpiler to render static text, against a requirement to be fast on a phone. Astro was considered and dropped as needing a toolchain for a two-reader page.

`web-report/` holds the site; `web-report-design/` holds design exploration.

## Users

**Primary: the project owner**, reading minutes before standup to decide what to raise. Success is extracting the two or three things that must be said out loud, fast, on a phone or a laptop.

**Secondary: the co-founder and leadership.** They read it to supervise delivery without opening the Zoho board or the repositories themselves — for them the report *is* the view of the project. Supervisors are readers of this report, not subjects of it: no one whose work is untracked appears as a measured row.

The delivery team is **not** a confirmed audience, and neither are investors or any external party. Nothing in the current report is written for people outside leadership.

## Product Purpose

Turn the dated Markdown project-status reports in `project-status/` into a readable, decision-ready web surface.

The reports already exist and already work — they are written by judgement in the `beevia-refresh` skill, not generated by script. This product does not change what a report says. It makes an existing report faster to read, faster to navigate, and legible on a phone, and it gives past reports a home you can get back to.

Success: the owner opens it on a phone before standup and leaves knowing what to raise, without scrolling through a 500-line Markdown file.

## Positioning

A generic project dashboard reports the board. This report reconciles **three independent evidence streams against each other** — the Zoho Sprints board, the actual commit history across five repositories, and the diffed API surface (105 consumer endpoints, 29 admin) — which is what lets it say things the board alone cannot, such as "the board recorded nothing for two days; the repos took 13 commits and five new endpoints in the same window."

The disagreement between sources is the product. Any design that presents the report as a tidy dashboard of board metrics destroys the thing that makes it worth reading.

## Operating Context

- **Cadence:** dated reports, currently daily during an active sprint. Three exist so far: 2026-08-05, 2026-08-06, 2026-08-07, at `project-status/project-status-YYYY-MM-DD.md`.
- **Generation:** the `beevia-refresh` skill runs a sprint export from the Zoho Sprints API, fast-forwards the five sub-repos, and runs an API drift audit — those three steps are scripted. Updating the OpenAPI specs and writing the report are done by judgement, per report.
- **Sibling artifacts at the workspace root:** `Beevia_PRD.md` (the product being built), `Beevia Admin Dashboard.md`, `api-rfc.md`, `admin-api-rfc.md`, four OpenAPI specs (shipped and proposed, consumer and admin), and `sprint-board-exports/`.
- **Reading scenes:** laptop browser full-screen, and phone shortly before standup. Both are first-class; mobile is not a downgrade of the desktop layout.
- **Not a reading scene (unconfirmed):** screen-sharing in a call, and emailing the report as a file. Do not design for these without asking.

## Capabilities and Constraints

**Content source — the report is written twice, by the same hand.** The Markdown report at `project-status/` remains the archive and the narrative source of truth. The skill writes the matching HTML page in the same authored pass. No parsing, no data pipeline, and no structured sidecar: the writer already knows the numbers when writing the prose, so marking up a table costs nothing and a schema would only be a way of re-deriving what was already in hand.

Numbers that recur across all three existing reports, and so deserve consistent visual treatment: sprint id and window; done / in-review / in-progress counts with day-over-day deltas; review-queue median and oldest age; consumer and admin API endpoint counts; and a per-person row of owns / submitted / cycle time / WIP / commits.

**The section structure is not fixed.** This is the hardest constraint. The 08-05 report has five numbered sections; the 08-07 report has seven, with sub-sections. Section titles are authored per report ("REVIEW/QA still has no exit", "Output is steady; acceptance is zero"). Only two elements are stable across every report: the **Quick overview** block at the top and the **Appendix — method** at the bottom. A renderer that assumes a fixed schema of sections will break on the next report, and the writer must never be forced to bend a report into a template to make the site render it.

**Archive scope: navigation only.** A dated list to open any past report. Cross-date trend charts, recommendation follow-through tracking, and two-date comparison were each considered and explicitly declined. Each report stands alone, as it does today. (The reports handle follow-through in prose themselves — the 08-07 report has a "Previous recommendations — where they stand" section.)

**Repository constraint (`.claude/rules.md`).** The five sub-repositories — `beevia-admin`, `beevia-admin-api`, `beevia-api`, `beevia-db-schema`, `beevia-mobile` — must not be modified. Git synchronisation by the `beevia-refresh` skill is the sole standing exception. All output belongs at the workspace root or in `project-status/`. This product lives in `web-report/` and touches nothing inside a sub-repo.

**Undecided:** the sidecar schema; whether the site is deployed anywhere or opened locally; whether report writing becomes partly automated later.

## Brand Commitments

None established. The product name in the reports is "Beevia — Project Status". No logo, colour, typeface, or voice constraint has been set for this surface.

The **report's own voice** is a real and deliberate asset, however, and is a product fact rather than a style choice: direct, quantified, willing to name what did not happen, and careful to separate measurement gaps from findings (the reports distinguish "blank Epic column because the API token lacks a scope" from "no epics exist"). It also states what its numbers do not measure. Design must not soften or dress up that voice.

## Evidence on Hand

- Three real dated reports at `project-status/project-status-2026-08-0{5,6,7}.md` — the only real content, and enough to design against. The 08-07 report is the richest.
- Real sprint data in `sprint-board-exports/`, refreshed from the Zoho Sprints API.
- Four real OpenAPI specs at the workspace root, source of the endpoint counts.
- A confirmed team roster in `.claude/skills/beevia-refresh/SKILL.md`, verified by the project owner after an earlier report inferred roles from activity counts and got one badly wrong.

**Do not fabricate.** There are no additional reports, no historical trend series beyond these three dates, no user research on this surface, and no deployment. Real names of real colleagues appear throughout the reports — invented people, invented metrics, and invented dates are out of bounds even in mockups. Design with the three real reports.

## Product Principles

1. **The report is the product; the site is the reading of it.** Never rewrite, summarise, or soften a report's content to fit the design. If a layout only works when the prose is trimmed, the layout is wrong.
2. **Structure must bend to the writer, not the writer to the structure.** Section count, titles, and depth change every report. Render what is there.
3. **Reconciliation is the value.** Where the board and the code disagree, the design must let that disagreement land, not average it into a neutral metric.
4. **Decisions in the first screen.** The primary read is minutes before a standup. The overview block, its deltas, and the things worth knowing must resolve before any scrolling — on a phone.
5. **Honest about its own limits.** The reports mark measurement gaps and state what they do not measure. Those caveats are content, not fine print, and must not be visually demoted into invisibility.

## Accessibility & Inclusion

No product-specific standard has been established. Two facts from the operating context do bear on it: the report is dense with tabular data, which must remain navigable and legible at mobile width; and it is read under time pressure, which raises the cost of low-contrast or small-set type.
